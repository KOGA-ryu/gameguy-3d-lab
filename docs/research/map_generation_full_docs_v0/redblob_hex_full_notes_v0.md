## 3. Relevant Technical Concepts

- Prefer cube coordinates for algorithms and axial coordinates for storage.
- Cube coordinate invariant: `q + r + s = 0`.
- Axial coordinate stores `(q, r)` and derives `s = -q - r`.
- Offset coordinates store `(col, row)` for rectangular arrays but parity affects neighbor deltas.
- Doubled coordinates are an alternative to offset coordinates with parity constraint `(col + row) mod 2 == 0`.
- Hex algorithms become straightforward when expressed as vector operations: add, subtract, scale, lerp, distance, rotate, and round.
- Hex maps can be stored as hash tables keyed by axial/cube coordinates for arbitrary shapes, or rectangular arrays with an adapter for fixed offset/doubled layouts.
- Hexes have six sides/edges and six corners/vertices; corners are generated by rotating around a center by 60-degree increments.
- Pixel conversion requires layout orientation, size, and origin. The inverse path subtracts origin, divides by size, converts to fractional axial/cube, then rounds.

## 4. Relevant Data Fields / API Fields / Formulas

### Coordinate Structures

```text
Cube / Hex:
  q: int
  r: int
  s: int
  invariant: q + r + s == 0

Axial:
  q: int
  r: int
  derived_s: -q - r

Offset:
  col: int
  row: int
  offset_type: odd-r | even-r | odd-q | even-q
```

### Cube/Axial Conversion

```text
axial_to_cube(q, r):
  s = -q - r
  return (q, r, s)

cube_to_axial(q, r, s):
  assert q + r + s == 0
  return (q, r)
```

### Offset Conversion

Use `offset = +1` for even and `offset = -1` for odd as in Red Blob's implementation guide.

```text
qoffset_from_cube(offset, h):
  col = h.q
  row = h.r + floor((h.q + offset * (h.q & 1)) / 2)

qoffset_to_cube(offset, col, row):
  q = col
  r = row - floor((col + offset * (col & 1)) / 2)
  s = -q - r

roffset_from_cube(offset, h):
  col = h.q + floor((h.r + offset * (h.r & 1)) / 2)
  row = h.r

roffset_to_cube(offset, col, row):
  q = col - floor((row + offset * (row & 1)) / 2)
  r = row
  s = -q - r
```

Implementation note: `& 1` avoids language differences in `%` for negative coordinates. If Build Dex uses Python only, `% 2` is safe for parity; for Rust/C/C++/JS, prefer `& 1` or an explicit Euclidean parity helper.

### Neighbor Directions

Cube directions:

```text
0: (+1,  0, -1)
1: (+1, -1,  0)
2: ( 0, -1, +1)
3: (-1,  0, +1)
4: (-1, +1,  0)
5: ( 0, +1, -1)
```

Axial directions from cube `(q, r)`:

```text
0: (+1,  0)
1: (+1, -1)
2: ( 0, -1)
3: (-1,  0)
4: (-1, +1)
5: ( 0, +1)
```

Diagonal cube directions:

```text
(+2, -1, -1), (+1, -2, +1), (-1, -1, +2),
(-2, +1, +1), (-1, +2, -1), (+1, +1, -2)
```

### Distance

```text
cube_distance(a, b):
  dq = a.q - b.q
  dr = a.r - b.r
  ds = a.s - b.s
  return (abs(dq) + abs(dr) + abs(ds)) / 2
  equivalent: max(abs(dq), abs(dr), abs(ds))

axial_distance(a, b):
  dq = a.q - b.q
  dr = a.r - b.r
  return (abs(dq) + abs(dq + dr) + abs(dr)) / 2
```

Euclidean axial metric from the guide:

```text
sqrt(dq*dq + dr*dr + dq*dr)
```

### Range

For a center and radius `N` in axial/cube:

```text
for dq in -N..+N:
  for dr in max(-N, -dq-N)..min(+N, -dq+N):
    ds = -dq - dr
    emit center + (dq, dr, ds)
```

Intersecting ranges are handled by intersecting min/max constraints for `q`, `r`, and `s`, then enumerating the constrained axial region.

### Rings And Spirals

Ring of radius `N`:

```text
start = center + direction[4] * N
for side in 0..5:
  for step in 0..N-1:
    emit current
    current = neighbor(current, side)
```

Spiral:

```text
emit center
for radius in 1..N:
  emit all cells in ring(center, radius)
```

Use rings for radius bands, roads around centers, radial scan, and visual proof overlays. Use range for fill regions and movement.

### Line Drawing

Line from hex `a` to `b`:

```text
N = cube_distance(a, b)
for i in 0..N:
  t = i / N
  point = cube_lerp(a, b, t)
  emit cube_round(point)
```

Nudge endpoints by tiny epsilon if deterministic tie-breaking is needed for exact boundary cases.

### Rounding

```text
cube_round(frac):
  q = round(frac.q)
  r = round(frac.r)
  s = round(frac.s)
  q_diff = abs(q - frac.q)
  r_diff = abs(r - frac.r)
  s_diff = abs(s - frac.s)
  if q_diff > r_diff and q_diff > s_diff:
    q = -r - s
  else if r_diff > s_diff:
    r = -q - s
  else:
    s = -q - r
  return (q, r, s)
```

### Hex-To-Pixel

For pointy top axial:

```text
x = size * (sqrt(3) * q + sqrt(3)/2 * r)
y = size * (3/2 * r)
```

For flat top axial:

```text
x = size * (3/2 * q)
y = size * (sqrt(3)/2 * q + sqrt(3) * r)
```

Apply origin after conversion:

```text
pixel.x = x + origin.x
pixel.y = y + origin.y
```

### Pixel-To-Hex

For pointy top:

```text
q = (sqrt(3)/3 * x - 1/3 * y) / size
r = (2/3 * y) / size
round axial/cube
```

For flat top:

```text
q = (2/3 * x) / size
r = (-1/3 * x + sqrt(3)/3 * y) / size
round axial/cube
```

If using a non-zero origin, subtract origin before inversion.

### Corners

For a hex center `(cx, cy)`, size `size`, and corner index `i`:

```text
angle_deg = 60 * i + start_angle
angle_rad = PI / 180 * angle_deg
corner = (cx + size * cos(angle_rad), cy + size * sin(angle_rad))
```

Use `start_angle = 30` for pointy top and `0` for flat top in Red Blob's convention.

## 5. Minimal v0 Subset For Our Engine

- Store cells as axial `q, r` plus derived `s`.
- Validate `s == -q - r` wherever `s` is stored.
- Keep `z`/elevation separate from hex coordinate `s`; our 32x32x8 cube uses `z` for vertical cells/meters, not Red Blob cube `s`.
- Use axial neighbor directions for terrain adjacency and edge profile generation.
- Use `axial_distance`, `range`, `ring`, and `line` for paths, roads, influence ranges, and chunk-local queries.
- Use hash-map storage keyed by `"q,r"` for v0 unless a rectangular adapter is explicitly needed for export.
- Use pointy or flat orientation consistently. Current repo should choose one layout per `hex_grid.layout` and write it into the recipe.
- Use hex corner generation for visible face meshing and top-face outline vertices.

## 6. Direct Project Mapping

- `32x32x8 map cube`: Red Blob gives x/y hex indexing; repo cube supplies bounded x/y/z volume and vertical `z`.
- `hex/elevation cells`: `q,r,s`, `base_height`, `fold_offset`, `final_height`, six edge profiles.
- `terrain mesh compiler`: generate top hex polygons from corners; generate side faces where neighbor height differs or neighbor is absent.
- `visible face meshing`: emit top faces for every buildable/walkable surface and vertical faces for cliffs/ledges/boundaries.
- `seam/fold grammar`: classify six neighbor deltas using Red Blob directions and repo edge types.
- `road/path layer`: use hex line/range/ring algorithms for roads, areas of effect, chokepoints, and bridges.
- `building plot layer`: map plot footprints to axial ranges or polygons, then record sockets on neighbor directions.
- `asset placement layer`: use corners/edges/centers for socket anchors; use direction index `0..5` for orientation.
- `Blender proof renderer`: convert axial centers and corner points to world-space mesh vertices.
- `future AI affordance graph`: hex cells are graph nodes; six neighbor edges carry movement/visibility/build tags.

## 7. Deferred Parts

- Wraparound maps.
- Non-regular hexes except explicit pixel stretch for preview.
- Doubled coordinates unless a Tiled-style rectangular export needs them.
- Direct offset-coordinate algorithms beyond conversion wrappers.
- Field of view until AI affordance work begins.
- Pathfinding details beyond graph neighbor/distance support.

## 8. Risks / Ambiguity

- Red Blob cube `s` is not vertical; repo `z` is vertical. Keep names explicit.
- Offset parity bugs are likely if Build Dex uses `%` in a language with truncated remainder.
- Pixel-space y axis differs between screen coordinates and Blender/world coordinates. Decide a y-down or y-up conversion boundary.
- Hex orientation must be fixed per map; mixing pointy and flat top will break neighbor and corner orientation.
- `32x32x8` is a bounded container, not necessarily 32 axial columns by 32 rows unless the map cube contract says so.
